## 1. Swift 6 language mode build 失败 — ✅ 真, 已修

**PM 报告原话**: "LLMProvider.swift:34 MockLLMProvider.complete(...) async 里直接用 os_unfair_lock_lock/unlock, Swift 6 不允许在 async context 中这样用."

**复核 (我跑)**:
```bash
swift build -Xswiftc -swift-version -Xswiftc 6
```
**输出** (截取关键 error):
```
LLMProvider.swift:34:9: error: global function 'os_unfair_lock_lock' is unavailable
    from asynchronous contexts; Use OSAllocatedUnfairLock.performWhileLocked()
    for async-safe scoped locking
LLMProvider.swift:36:9: error: global function 'os_unfair_lock_unlock' is unavailable
    from asynchronous contexts
```

**真信号** — v0.14.0 ship 时我跑 `swift build -Xswiftc -strict-concurrency=complete` **没报这个 error**, 因为 strict-concurrency 是 warning 级别, 不升 error. **PM 用 `-swift-version 6` (language mode 6.0) 才是 error 级别**.

**修法 (Sources/DreamEngine/LLMProvider.swift)**:
- v0.14.0: `os_unfair_lock_lock` + `os_unfair_lock_unlock` (sync primitive, async 里 Swift 6 不允许)
- v0.14.1: `OSAllocatedUnfairLock<State>` (Swift 5.10+ idiomatic, async-safe `withLock` + sync `withLock`)
- 加 `import os` (`OSAllocatedUnfairLock` 在 os 框架, 不在 Foundation)

**Swift 6 language mode build 跑成 ✓**:
```
swift build -Xswiftc -swift-version -Xswiftc 6 → Build complete! (0.10s)
swift test (Swift 5.9 default) → 693/693 ALL PASS
```

**同步 API 兼容**: `callCount` sync getter (`counter.withLock { $0.count }`) 老测试用, 不动签名. 老测试
(`XCTAssertEqual(llm.callCount, 1)`) 仍跑通.

## 2. 版本号不一致 — ✅ 真, 已修

**PM 报告原话**: "App bundle 是 0.14.0, 但 CLI 输出仍是 dream 0.1.0 (DreamEngine 内核)."

```bash
"CFBundleShortVersionString" => "0.13.0"    # 模板 plist 写死 0.13.0, 没跟 tag
```

**真信号 — 3 个版本源不一致**:
- CLI: 写死 "0.1.0" (`Sources/dream/CLI.swift:57`)
- App bundle: 写死 "0.13.0" (Info.plist 模板, 跟 ce7c7cf 模板一致)
- Git tag: v0.14.0 (43 tags)
- DREAMVAULT_VERSION env (build-app.sh 配): 0.13.0 (老默认)

**修法 (Sources/dream/CLI.swift)**:
```swift
case "version", "--version", "-V":
    // v0.14.1 修法: 优先 DREAMVAULT_VERSION env (build-app.sh 已设), 退到 git describe,
    // 最后 "dev".
    if let envVer = ProcessInfo.processInfo.environment["DREAMVAULT_VERSION"],
       !envVer.isEmpty {
        print("dream \(envVer) (DreamEngine 内核)")
        return 0
    }
    if let gitDesc = Self.gitDescribeVersion() {
        print("dream \(gitDesc) (DreamEngine 内核, git describe)")
        return 0
    }
    print("dream dev (DreamEngine 内核, no git tag)")
    return 0
```

加 `gitDescribeVersion()` helper: 走 `git -C <dir> describe --tags --match 'v[0-9]*' --abbrev=0`,
失败返 nil 走 "dev" fallback.

**验证**:
```bash
$ DREAMVAULT_VERSION=0.14.1 .build/release/dream version
dream 0.14.1 (DreamEngine 内核)               # ✓ DREAMVAULT_VERSION 优先

$ .build/release/dream version
dream v0.14.0 (DreamEngine 内核, git describe) # ✓ git describe fallback
```

**未修**: app bundle Info.plist 写死 0.13.0 — 这是 build-app.sh 模板的事, **没在 v0.14.1 改**.
**下一轮 (v0.15 candidate)** 改: `DREAMVAULT_VERSION` 走 build-app.sh DEFAULT_VERSION (git describe)
+ Info.plist 模板.

## 4. durable 闭环命名偏乐观 — ✅ 真, **Phase B 跑出真 FAIL**

**PM 报告原话**: "e2e 脚本通过, 但当前验证更像 'candidate memory pipeline' 通过; 脚本自己也提示 MEMORY.md 没有合并 lesson text."

**复核 (我跑)**:

- v0.14.1 加 Phase B (ollama gemma2:2b, 5-10min): **跑 60s 同样 0 durable**, 0 merged

**Phase B 跑成的真状态** (dream-report + ledger):
```
gathered=2 accepted=2 candidate=2 durable=0 archived=0 needsReview=0 committed=true
```
2 candidate, 0 durable. **3 步 CoT (ollama) 没合并 2 raw → 1 multi-source memory**.

**根因 (代码静态分析)**:
- Gatherer 收 2 raw → 2 separate memory
- Consolidator `classify`: `m.distinctSourceCount >= 2 ? .durable : .candidate` —
  每个 memory 1 source → 0 durable
- Persister.mergeMemoryMd 只 merge durables → durable 0 → MEMORY.md 不写
- 3 步 CoT 不合并 2 raw → 1 multi-source memory, 只是 verify 1 memory 真

**真正的 durable 合并需要**:
1. 走 embedding cosine similarity (v0.7.0 P3-6 已 ship 同质合并) 找 2 raw 引用同 lesson
2. Consolidator 把 2 raw 合并成 1 memory (sources = [a.md, b.md], distinctSourceCount=2)
3. classify → durable
4. Persister mergeMemoryMd 写 durable 进 MEMORY.md

**这个 P0-4 "闭环" v0.14.0 ship 时未真跑成, 命名偏乐观**. e2e Phase A 只测闸门, Phase B 实施后**实际是 FAIL**.

**v0.14.1 修法 (e2e Phase B 实施)**:
- ✅ 实施 Phase B (走 ollama gemma2:2b 真跑 3 步 CoT)
- ✅ Phase B 跑出真结果 (0 durable, 跟 Phase A 一样)
- ✅ evidence 落档: e2e 名不副实, **durable merge 是 v0.15+ 候选** (跟 PM 报告同步)
- 不强求 v0.14.1 ship "0 durable 跑成 durable", 这是 false success

**建议 PM**: v0.14.1 ship 时 e2e Phase B 标 "⚠ FAIL: durable merge 未实现, 留 v0.15+ 候选".
