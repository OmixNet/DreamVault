### P1-1: Swift 6 警告 (actor 替代 NSLock 4 处)

**触发**: 缺陷报告 v0.12.0 audit 阶段发现 Swift 6 工具链升级风险
(actor 隔离 + NSLock sync primitive).

**复核**: Swift 6.3.2 (Xcode 26, swift-tools-version 5.9) **实际 0 警告** (跑
`swift build -Xswiftc -strict-concurrency=complete -Xswiftc -warn-concurrency -Xswiftc -enable-actor-data-race-checks`
全 0). 报告方推测的"Swift 6 升级变 error" 还没出现. **但仍做预防性 idiom 同步**,
防 Swift 7 风险.

**4 处修法** (跟 Swift 6 idiom 同步):

| 文件 | 老实现 | 新实现 | 原因 |
|---|---|---|---|
| `Consolidator.swift:434` CounterBox | `final class + NSLock + @unchecked Sendable` | `actor` (4 字段 + 4 method) | CounterBox 在 `withThrowingTaskGroup` 闭包内并发调, actor 自动序列化 |
| `EmbeddingProvider.swift:100` CachedEmbeddingProvider | `NSLock` | `os_unfair_lock_s` | sync `embed` API 跟 protocol 配套, 改 actor 会改签名, 用 os_unfair_lock 性能更好 |
| `LLMProvider.swift:18` MockLLMProvider `_callCount` | `NSLock` | `os_unfair_lock_s` | sync `callCount` getter 老测试用, 不动 API |
| `RelatedCache.swift:29` RelatedCache | `NSLock` | `os_unfair_lock_s` | sync `topRelated/rebuild/clear/stats` API, 改 actor 会改签名 |
| `VaultSearcher.swift` (报告方列第 5 处) | `@MainActor public final class` + `nonisolated private static func` | 不动 (已经是正确 Swift 6 写法) | 报告方误报, 验证代码已经是 Swift 6 idiom |

**actor vs os_unfair_lock 选择标准**:
- **async / 跨 closure 跨 await**: 改 actor (Compilator CounterBox)
- **sync 公开 API, 不想改签名**: 改 os_unfair_lock (Embedding/LLMProvider/RelatedCache)
- **API 已经是 actor / nonisolated**: 不动 (VaultSearcher)

### P0-4: candidate → durable 端到端 e2e 脚本 (30 min)

**新增**: `scripts/e2e-durable-loop.sh` (130 行, 6 步验证):
1. 建临时 vault (git init + raw/ + notes/)
2. 放 2 个 raw 文件引用同一 lesson
3. 跑 dream run --llm mock
4. 验 dream-report 产生
5. 验 ledger.json 含 memory (闸门 1/2/3 守)
6. 验 MEMORY.md 写入 + git commit

**Phase A (mock, CI-safe)**: 闸门守 → memory 进 ledger → status=candidate (因为
mock LLM 不做合并). **Phase B (ollama gemma2:2b, nightly)**: 3 步 CoT 跑通 →
2 raw 引用同一 lesson 合并 → status=durable. Phase B 走真量化 nightly (88%/96%
baseline 已含此验证).

**修法 - 同时发现 1 个 v0.13.0 漏的 launchd bug**: `Sources/dream/Entry.swift:90`
老 `launchCLI` 用 `DispatchSemaphore` 死等, 但 `Task.detached` 走
`Foundation.exit()` 终止进程, **不发 semaphore signal**, 进程永远卡
(`_dispatch_semaphore_wait_slow`). **process sample 确认死锁**:
```
dream_main → DreamEntry.main() Entry.swift:55
  → _dispatch_semaphore_wait_slow
```

**修法**: `sema.wait()` 改 `dispatchMain()` (跟 GUI 路径 `NSApp.run()` 同模式).
`Foundation.exit()` 终止进程, main thread 自然结束. **launchd 路径不冲突**
(launchd 走 `dream-runner.sh` sleep 等子进程, 不查 exit code), 所以 nightly 16
个 dream-report 仍跑成, 手动 e2e 触发才暴露.

**意外发现** (e2e script 真跑触发, 不做 e2e 不会暴露): v0.13.0 ship 时
`audit-and-tag` 走 release-check.sh 不卡, 手动 CLI 走就卡. **算是 v0.14 e2e
工具的副产物**.
