# v0.7.0 — P3-5 follow-up 切 4 调用到 StructuredParser

## 评审发现 (P3-5 §4.2 follow-up)

P3-5 搭了 4 schema (`VerifyResponse` / `ConflictResponse` / `AnalysisResponse` / `DraftListResponse`) + `StructuredParser` + `LLMSchema.jsonSchema(for:)` 整套基础设施, 但**4 个生产路径 (Consolidator.analyze / generate / verify / ContradictionDetector.conflicts) 仍用老 keyword 解析**, 走 `contains("YES")` / `contains("CONFLICT")` / `parseDrafts` / `parseAnalysis` 等老路径. 评审 §2.3 / §2.4 强调这是 LLM 输出不稳定时的雷.

## 修复

### 切 4 调用到 StructuredParser (主路径), 老 keyword 解析保留作 fallback

| 切点 | 调用 | Schema | Fallback |
|------|------|--------|----------|
| 1. verify 阶段 | `Consolidator.verify` → `parseVerifyAnswer` | `VerifyResponse` (.yes/.no) | `contains("YES")` (老 keyword) |
| 2. conflict 阶段 | `ContradictionDetector.parseConflictAnswer` | `ConflictResponse` (.ok/.conflict/.ambiguous) | P3-2 keyword 三层降级 (NO CONFLICT 等) |
| 3. analyze 阶段 | `Consolidator.parseAnalysis` | `AnalysisResponse` | 老 `Analysis` struct 解析 (字段完全一致) |
| 4. generate 阶段 | `Consolidator.parseDrafts` | `DraftListResponse` | 老 `[MemoryDraft]` array 解析 |

### 关键 invariant 保留

- 老 keyword 输入 ("YES" / "NO" / "CONFLICT" / "OK") 仍正确解析 (向后兼容)
- 老 JSON `{"conflict": false}` 仍正确解析 (P3-2 老格式兼容)
- P3-2 "NO CONFLICT" 仍判 false (主路径 enum 约束 `.ok` / `.conflict` / `.ambiguous`, 不再走 keyword 模糊)
- 真 LLM (Ollama 走 `format: json_schema` 约束) 主路径走 StructuredParser, 偶尔 schema 出格 fallback
- mock provider 走老 keyword 路径 (`defaultHandler` 返 "YES" / "NO" / "CONFLICT", 老解析仍能解), 0 退化

### 桥接

- `AnalysisResponse` 字段跟 `Analysis` struct 完全一致 (keyEntities / keyConcepts / tensionsWithExisting / recommendedLessonTexts / reasoning / recommendedKind), 1:1 桥接
- `DraftListResponse.DraftItem` 跟 `MemoryDraft` 字段差 1 个 (P3-5 schema 用 `kind`, 老 struct 用 `kindRaw`), 桥接映射 1 字段
- `MemoryDraft.decayClassRaw` / `kindRaw` 容错 (P3-5 schema 收 `decayClassRaw`, 跟老同), 字段对齐
