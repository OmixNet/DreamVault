# v0.6.4 — P3-5 评审 §4.2 修复 (LLM 结构化输出)

## 评审发现 (§4.2)

4 个 LLM 调用 (verify / conflicts / analyze / generate) 各自走**老** 解析:
- `contains("YES")` / `contains("NO")` (verify)
- `contains("CONFLICT")` / `contains("OK")` (矛盾)
- `stripMarkdownFence` + `JSONDecoder` (analyze, generate)

解析雷多: 否定词窗口, 围栏, 标点, 大小写, 截断响应. 一次改造, 2.3 (verify NO) + 2.4 (CONFLICT 解析) 同时消失.

## 修复

- **4 schema 统一**: `VerifyResponse` / `ConflictResponse` / `AnalysisResponse` / `DraftListResponse`
  (Codable struct). 端到端共用一份定义.
- **LLMSchema.jsonSchema(for:)** → Ollama `format: json_schema` 字段需要的 JSON Schema dict
  (含 enum 约束 YES/NO, OK/CONFLICT/AMBIGUOUS, slow/normal/fast, entity/concept/synthesis).
- **LLMSchema.detect(fromSystemPrompt:)** → 自动从 system prompt 关键词判 phase
  (跟老 mock defaultHandler 走同款: 事实校验器 / 互相矛盾 / 分析师 / 提炼员).
- **OllamaNativeProvider** 走 Ollama 原生 `/api/chat` 端点 + `format: json_schema` 约束生成.
  跟老 `OllamaProvider` (OpenAI 兼容) 并存, 向后兼容.
- **StructuredParser.parse(_:as:schema:)** 容错解析: 剥 ` ```json ` 围栏, 抛错带 schema 名 + raw 前 200 字符.

## 集成 (未来工作)

当前 4 个调用方仍用 `parseAnalysis` / `parseDrafts` / `parseConflictAnswer` (容错关键字解析).
P3-5 提供了**可观测的 schema 工具** + `OllamaNativeProvider`. 后续 P3-5 follow-up:
- `Consolidator.analyze/generate/verify` 走 `StructuredParser.parse(..., as: AnalysisResponse.self, schema: .analyze)`
- `ContradictionDetector.detect` 走 `StructuredParser.parse(..., as: ConflictResponse.self, schema: .conflict)`

## MockURLProtocol 测试踩坑

`URLProtocol` 走**类**派发 (注册 `protocolClasses = [MockURLProtocol.self]`), **不**是实例.
状态必须走 `static` (类共享) 才能被 URLSession 实例化时拿到. 设计:
- `static var currentHandler: ((URLRequest) -> (statusCode, bodyJSON))?` (每个 test setUp 改)
- `static var lastRequest` / `static var lastRequestBodyJSON` (记录请求, test 断言)
- `instance var` 不可用 (URLSession 实例化时新建, 默认 200/{})
