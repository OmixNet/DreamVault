# v0.6.3 — P3-4 评审 §2.6 修复 (Gatherer 分块 + 真实化 sourceLine/excerpt)

## 评审发现 (§2.6)

50KB Claude session 日志被 `Ollama num_ctx=2048-8192` 静默截断. analyze 只看到开头,
后半段教训无声丢失, 且无任何告警. 现有 excerpt 恒 200 字符, sourceLine 恒正文首行,
引用粒度名不副实.

## 修复

- `Gatherer.maxChunkChars` 默认 **4000 字符** (安全线 < Ollama num_ctx=8192, 留 ~50% 给
  analyze + generate prompt + 余量). 单文件多分块 → 多 candidates.
- `Gatherer.chunkBody(_:maxChars:)` 按 markdown `## ` (H2) split:
  - 短 body (≤ maxChars) → 1 块 (短 raw 不浪费 LLM 算力, 跟 1 文件 = 1 candidate 兼容)
  - 长 body → intro + 1 块 per H2
  - 单块超 maxChars → 强制按 `\n` 切 (优先选最近 `\n` 切 AFTER, 保留词完整避免切到单词中间)
  - 空 body → 0 块
- `Gatherer.annotateChunksWithLineNumbers(_:fullBody:bodyStartLine:)` 给每块标注
  在原文件中的起始行号 (1-based). 真实化 `sourceLine`, 不再恒为 `bodyStartLine`.
- `GatherResult.chunkStats: [relPath: ChunkStat]`. `ChunkStat { chunks, truncated, originalChars }`
  给 dream-report / `onStage` 给用户审查分块数 + 截断告警 (`truncated=true`).
- `SourceRef.excerpt` 真实化 = `chunk.text`, 不再恒 200 字符 (引用粒度名不副实修复).
- **P0-3 闸门 substring check 兼容**: `chunkBody` 切分时**不 trim**, chunk 必是
  `sourceContents[relPath]` (= 脱敏后 body) 的连续 substring.

## 集成

- `DreamCycle.onStage` 报告分块 summary: `"file.md:3c⚠️, file2.md:1c"`.
  长文件分块数 + ⚠️ 截断告警直接在 stage 报告里.
